# 系统加强计划

本文记录后续服务端化和规模化前需要补齐的系统防护能力。它不是当前功能实现清单；没有明确进入对应开发轮次前，不应为这些条目提前新增后端表、接口或迁移。

## 原则

- 产品表面保持轻：用户不应看到容量、过期、清理、限流等系统维护语言。
- 防护靠后端兜底：前端限制只用于体验优化，不能作为安全边界。
- 数据少存、短存、可清理：轻应用产生的高频临时内容默认不进入长期业务真相。
- 核心对象优先：只有会长期驱动身份、权限、内容、事件或状态的事实才进入核心对象；应用临时态优先放应用附属表或缓存层。

## 喝彩便签服务端化防护

当前喝彩便签原型只使用浏览器本地状态，不会写入服务端数据库。后续如果接入服务端保存，每个实体实例必须先补齐以下防护，再开放写入。

### 数据边界

- 喝彩便签不是任务管理系统，服务端只保存当前可见的“见面理由”。
- 每个实例最多保留 `100` 条当前在线内容。
- 每条内容默认 `24h` 后过期，过期后从用户可见状态中移除。
- 过期未完成内容不向用户展示，不形成历史清单。
- 如需统计，只记录不可逆聚合事件，例如过期数量，不保存原文。

### 写入限制

- 单条文本长度必须由服务端限制，建议 `1-80` 个用户可感知字符。
- 服务端负责 trim、空内容拒绝、异常 Unicode 归一化和最大字节数限制。
- 同一实例需要短窗口限流，例如 `10/min`。
- 同一实例需要日限流，例如 `80/day`。
- 同一账号或匿名指纹需要更宽的写入限流，例如 `300/day`。
- 同一 IP 地址只能作为辅助限流维度，避免办公、校园或家庭 NAT 误伤。
- 同一实例短时间重复文本应拒绝或合并，例如 `30s` 内相同文本只保留一次。

### 容量控制

- 写入前先清理该实例已过期内容。
- 清理后仍超过 `100` 条时，服务端应保留最新内容并收掉最旧内容。
- 容量控制不返回用户可见“已删除几条”的提示。
- 前端传来的 `expires_at`、`created_at`、`state` 不可信，服务端必须重新计算。

### 推荐表形态

```text
cheer_note_items
- id
- ip_instance_id
- owner_user_id nullable
- anonymous_fingerprint nullable
- text
- state: active / completed
- created_at
- completed_at nullable
- expires_at
```

推荐索引：

```text
(ip_instance_id, expires_at)
(ip_instance_id, created_at)
(owner_user_id, created_at)
(anonymous_fingerprint, created_at)
```

### 清理策略

- 每次写入前顺手清理当前实例过期内容。
- 后台定时任务全局清理 `expires_at < now()` 的内容。
- SQLite 场景下需要配套考虑 `vacuum` / compact 策略，避免文件删除后仍长期膨胀。
- 清理任务失败不应影响用户打开体验，但必须可观测、可重试。

### 事件与观测

- 高价值事实可写入事件，例如 `cheer_note.item_created`、`cheer_note.item_completed`。
- 高频写入、过期清理和拒绝写入应进入系统观测，不进入用户叙事。
- 攻击防护指标至少覆盖：实例写入速率、账号/指纹写入速率、拒绝次数、清理数量、表体积变化。

## 接入前检查卡

后续任何轻应用把临时用户输入接入服务端前，先回答：

- 是否真的需要服务端保存，而不是本地状态或短期缓存？
- 这份数据最长保留多久？
- 单实例、单账号、单指纹、单 IP 的写入上限是什么？
- 超过容量时是拒绝、覆盖、合并，还是只保留最新？
- 用户是否需要知道清理发生？如果不需要，前端不要暴露系统维护语言。
- 清理后数据库文件或对象存储是否会真正释放空间？
- 这份数据是否会进入事件账本？如果进入，事件是否只保存必要事实？
