# Development Standards

这份文档是 WhatMint 当前阶段的开发执行标准。目标不是追求“大而全”的规范体系，而是把已经反复出现的工程问题前置成硬约束，让后续功能开发默认就是收敛的。

## 适用范围

- 适用于 `tapu/` 下前端、后端、文案、样式、路由、OS 抽象和轻应用接入开发。
- 与 [engineering-governance.md](engineering-governance.md)、[os-app-boundary.md](os-app-boundary.md)、[route-permission-principles.md](route-permission-principles.md) 共同生效。
- 前端视觉与样式治理同时遵循 [design-system-governance.md](design-system-governance.md)。
- 如果三者冲突，优先顺序为：
  1. `os-app-boundary.md`
  2. `route-permission-principles.md`
  3. 本文
  4. `engineering-governance.md`

## 总原则

- 先复用现有范式，再新增实现。
- 先拆分再加功能，不把治理留到功能完成后补做。
- 先明确 OS / 应用边界，再决定代码放哪一层。
- 先把用户可见内容抽离，再写交互细节。
- 先通过检查链，再进入提交阶段。

## 文件体积约束

### 硬性规则

- 单文件超过 `500` 行时，新增功能必须主动评估拆分。
- 单文件超过 `900` 行时，不应继续直接堆叠业务逻辑，除非是紧急修复。
- 拆分动作应和当前开发一起完成，不要把“大文件整理”留到后续治理冲刺。

### 推荐拆分方式

- 页面文件：按“容器页面 + composable + 展示组件 + copy + 独立样式文件”拆分。
- 后端路由：按“路由注册 + handler 模块 + 领域 service”拆分。
- API 聚合文件：新增接口优先进入独立模块，再由入口统一 re-export。
- 样式密集页面：优先把整页样式迁到 `src/styles/*.css`，页面只保留结构。

### 禁止做法

- 明知文件已过大，仍继续把新业务直接塞进原文件。
- 只抽 DOM 片段，不抽状态、交互和数据逻辑，导致页面体积不降反升。

## 文案规范

### 用户侧文案

- 非管理端、非官方后台的用户可见文案，必须进入 `src/copy/*.ts`。
- 页面、组件、composable 中不直接写中文用户提示、按钮、说明、空态、toast 文案。
- 对客中文展示话术包含表单校验、toast、空态、确认弹窗和可恢复报错；这些都必须抽取，不只抽页面正文。
- 每个 copy 文件开头必须用简短注释说明它负责哪个模块、页面或错误面，方便后续统一优化话术和国际化迁移。
- 后端可能直接返回给前端展示的错误、权限提示和业务提示，必须进入 `server/copy/*`，不要在 route handler 或 service 中临时写字符串。
- 文案放置应按领域归档，例如：
  - 内容详情放 `content.ts`
  - 创作中心放 `studio.ts`
  - 用户资产放 `user.ts`
  - 商城 / IP 详情放 `shop.ts`

### 允许例外

- 图片文件名、IP 名称关键词匹配、受控 allowlist、数据字典值可以保留在代码中。
- 例外必须满足“不是用户文案，而是技术判定或资源标识”。

### 开发要求

- 新增文案时优先复用已有 copy 字段，不要重复造句。
- 同一业务语义不能在多个文件各写一份略有差异的版本。

## 样式规范

### 统一原则

- 相同视觉语义优先复用现有样式变量、公共样式类或模块样式。
- 如果两个以上页面出现相同设计语言，应抽到公共样式变量或共享样式文件。
- 新页面不要私自发明一套新的间距、圆角、按钮、状态色体系。

### 推荐做法

- 页面专属大样式放 `src/styles/*.css`。
- 全局 token、基础色、共享层级优先沿用现有变量。
- 新非管理端页面默认使用 `.wm-page` 与 `.wm-shell`，页面差异优先通过覆盖 semantic token 表达。
- 按钮、标签、面板、弹窗、空态和加载态优先使用 `design-system.css` 中的 `.wm-*` 基座类。
- 对客按钮、加载态和空/错状态优先使用 `src/components/common/WmButton.vue`、`WmLoading.vue`、`WmState.vue`；不要在页面里重新定义完整按钮系统。
- `/play`、NFC 触碰入口、OS entry prompt 和轻应用 runtime 都属于对客 OS 表面，必须遵守同一套按钮、loading、error state 规范。
- 同类卡片、按钮、表单控件保持一致命名和一致结构。

### 禁止做法

- 在多个页面复制同一段大样式后各自微调。
- 有现成 token / 模块样式仍重复写死颜色、阴影、圆角。
- 页面背景直接写一整套独立色板或硬分割背景，导致后续换风格必须逐页改。

## 路由与接口规范

### 后端接口

- 新接口必须按当前路由注册范式接入 `routePermissions`，不能裸写 Express handler。
- 每个接口都要明确：
  - permission type
  - operation
  - summary
  - request body / query shape
  - response shape
  - tags
- 权限类型选择遵循 [route-permission-principles.md](route-permission-principles.md)。

### 前端 API

- 前端不直接散写 `fetch`；统一通过 `src/api` 入口或其子模块。
- 新 API helper 命名应表达业务动作，不暴露底层路径细节。
- 新增轻应用接口优先放到对应领域模块，再由总入口导出。

### 路由设计

- 页面路由延续当前 router 组织方式，不平行再造新的后台壳或重复入口。
- token / key / ownership 相关跳转必须沿用当前白名单和解析路径，不要私自发散。

## OS / 应用边界规范

- OS 负责：身份、权限、事件、状态、runtime context、内容协议、技能匹配、Studio shell。
- 应用负责：故事表达、角色语气、节奏、领域数据、可见体验。
- 新功能如果同时碰到多个轻应用，优先思考是否应进入 OS 层复用。
- 新功能如果只是某个应用独有表达，不要提前平台化。

## 新增功能默认检查卡

开发完成前，至少自查一次：

- 文件是否因为这次改动继续明显膨胀；如果是，是否已经同步拆分。
- 用户文案是否全部进入对应 `copy` 文件。
- 新样式是否复用了现有变量或共享样式。
- 新接口是否走了权限注册和契约描述。
- 新路由是否沿用了现有组织方式，而不是平行造入口。
- 新能力是否符合 OS / 应用边界。

## 提交前检查

在 `tapu/` 目录至少执行：

```bash
npm run check:quality
npm run build
```

如本轮包含较大结构调整，还应补充：

- 关键页面手动回归
- 关键接口真实请求验证
- 必要的契约测试或诊断脚本

## 一句话执行要求

后续开发默认按这份标准执行：

- 文件过大时主动拆
- 文案新增时主动入 `copy`
- 相同样式主动收敛
- 新接口和路由主动按现有范式配置
- 不把工程治理留到功能完成后补做
